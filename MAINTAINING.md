# Maintaining squared-examples

The examples are educational tools and tests. Each proves a use case: how easy
or hard the framework is to use and understand, and how efficient it can be.
They are not a reference for the framework. The framework's source repository
and its documentation are the truth; an example may lag behind them.

## Each example is a whole workspace

An example is committed with its copy of the framework, `<example>/squared/`,
exactly as squared-pg vendors it into a generated workspace. A clone builds with
nothing else installed. Identical framework files are stored once by git, so
several examples at the same framework commit cost about one copy.

`<example>/SQUARED_REV` names the squared package commit that copy came from.

Never committed: build output (`<example>/build/`,
`<example>/squared/build/release/`, `<example>/squared/build/debug/`) and
`*.bak.*` files. `squared/build/common.mk` is source, and is committed.

## Framework code travels one way: package to example

The squared package (`resources/.squared/packages/package.squared-core` in
squared-pg) is the only place framework code is changed. A fix found while
working on an example is made in the package, committed there, and then brought
into the example. Never the other way.

The tools enforce it:

| Tool | Refuses when |
|---|---|
| `tools/vendor_framework.sh` | the example's `squared/` differs from the package commit it came from (the change belongs in the package); the package commit holds a `{{placeholder}}` |
| `tools/push_demo.sh` | the example's `squared/` is not byte-identical to the package commit it names |

`vendor_framework.sh` copies only committed package code (`git archive` of a
commit), so a fix must be committed to the package before an example can have it.

It writes only what changed: files the commit holds unchanged are left as
they are, timestamps included, and the framework's build output
(`squared/build/release`, `build/debug`) is kept, so the next `make` rebuilds
only what depends on the changed files. Written files get the current time;
files the commit dropped are removed. Replaced and removed files are backed up
to `~/.cache/squared-template-backups/<stamp>/<example>/squared/`, and only
those (before 2026-10-19 the whole tree moved there, build output and all, on
every run).

Copying is the same as generating only because the framework needs no
substitution: it holds no `{{placeholders}}`. `vendor_framework.sh` checks that
on every run. If it ever stops holding, examples must be refreshed through
squared-pg instead.

## Workflows

**Fresh clone.** Build as it is:

    cd squared-examples/demo && make DEV_LOG=1 apk && make install

**Bring an example up to the package.** After committing the change in the package:

    tools/vendor_framework.sh demo --latest
    (cd demo && make DEV_LOG=1 apk && make install)    # and check it on the device
    tools/push_demo.sh --push

**Restore an example's framework to the commit it records**, after a stray edit
or a deleted `squared/`:

    tools/vendor_framework.sh demo           # --force if squared/ has edits to discard

**A new example** is generated by squared-pg like any workspace, then mirrored in:

    tools/push_demo.sh --demo ~/sqsysroot/sandbox/<name> --dir <name> --msg "<name>: start"

## Not here: regenerating a workspace

squared-pg can generate a workspace, but cannot yet update one in place. The
framework doesn't need that (it is copied, as above). The template's own files
(`Makefile`, `mk/squared_*.mk`, `sq_android/entry.cpp`) do: when the template
changes, an example takes those changes by hand. Regeneration is planned after
Sprint 5 of the squared refactor.
